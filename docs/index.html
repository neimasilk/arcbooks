Why statements on Arc need care

On Arc, USDC is both the native gas token (18 decimals) and an ERC-20 (6 decimals) backed by the same balance. A single ERC-20 transfer() emits two Transfer logs: one from the USDC contract 0x3600…0000 (6 decimals) and one from the system emitter 0xffff…fffe (EIP-7708, 18 decimals). Plain native sends emit only the system log, and gas fees emit nothing at all. Naive indexers double-count, truncate sub-cent amounts, or silently miss fees.

ArcBooks reads only the system-emitter stream, so every movement is counted exactly once at full 18-decimal precision. It then reconciles: opening + in − out is compared with the onchain closing balance, and the difference is reported explicitly as fees and other non-logged movement.

Memos

Transfers sent through Arc's predeployed Memo contract (0x5294…e505) carry an invoice or order reference. ArcBooks joins Memo events to transfers by transaction, so each payment shows its reference. The Payment request tab creates links that pay this way.

Automated attestation with Chainlink CRE

The /cre folder contains ArcBooks Auto-Attest, a Chainlink Runtime Environment workflow written in Go. On a cron schedule it:

  • reads the latest header, the account's last checkpoint, archive balances, and USDC Transfer and Memo logs from Arc Testnet (EVM read);
  • rebuilds the same canonical CSV as this app, byte for byte (cross-tested against real mainnet and testnet data), and hashes it;
  • fetches a USD/IDR reference rate from an external FX API with median consensus across the DON (HTTP);
  • sends a signed report to ArcBooksAttestor (EVM write via the CRE forwarder).

Checkpoints form a hash chain over contiguous block ranges: each must start one block after the previous one and commit to its hash, so gaps, overlaps and rewrites are rejected onchain. The result is a tamper-evident, continuously audited USDC ledger that anyone can re-derive here. Attestor (Arc Testnet): 0xe048B7592D0aCb55f01d06013Df6961ABF9Fdb9C.

Verifiable statements

The canonical CSV is deterministic: the same address and block range always produce the same bytes. Its keccak256 hash can be anchored in the StatementRegistry contract. An auditor, bank, or tax consultant can check the hash and re-derive the statement from public chain data. No trust in the person who sent the file is required.
